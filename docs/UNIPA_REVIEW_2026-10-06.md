# UNIPA通知Adapterのコードレビュー

レビュー日：2026-10-06。対象は同一MCPに追加する本人専用の読み取り機能。出席登録・出席収集・掲示本文の取得・既読更新は含まない。

## 修正した指摘

| 優先度 | 問題                                                                                               | 修正と検証                                                                                                                                          |
| ------ | -------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1     | 同意画面のGETから承認POSTまでの間にUNIPA設定が有効になると、画面で示していない追加権限を付与し得る | 画面に示す権限を暗号化された同意トランザクションへ固定し、POST時には追加しない。設定変更を挟む回帰テストを追加                                      |
| P2     | JSF部分更新でViewState更新がフォーム置換より先に届くと、置換されたフォームの古い状態で上書きされる | DOM置換の完了後に最新ViewStateを全フォームへ適用する。状態入力が省略されたフォームにはhidden入力を作る。更新順序と入力の有無を2つの回帰テストで検証 |

認証済み所有者の照合、追加スコープ、外部originへの転送拒否、Cookieの扱い、一覧の完全性、失効・停止・キャッシュ、公開ファイルに資格情報が含まれないことを確認した。私的なブラウザ検証画像はGitの対象から除外している。

## 検証

`npm run check`で79テスト、TypeScript、Workerのdry-runビルド、Prettierを通過。workerdでは既存ClassroomのOAuth・取得・更新と、追加同意後のUNIPA通知取得・保存・ページ分割を合成データで検証した。本物のUNIPA資格情報・掲示・Cookieはテストに使っていない。

## 実機検証で残ること

本人のSecretsと専用KVを設定した後のCloudflareからのログイン・全件取得・CPU制限・既読状態・通常ログインへの影響は未検証。設定がない場合は既存Classroomの5ツールだけを提供する。

KVは分散ロックではないため、複数isolateの同時ログインを完全には防がない。最初は直列に検証し、実測で必要なら取得の直列化をDurable Objectへ移す。この制限と認証失敗時の再開手順はREADMEと実装文書に記載した。
